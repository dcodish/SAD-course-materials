מה זה Claude Code — ולמה זה לא צ׳אט

צ׳אט מחזיר טקסט. אתם מעתיקים, מריצים ומתקנים בעצמכם.

Claude Code הוא סוכן. הוא קורא וכותב קבצים בתיקייה שפתחתם, מריץ פקודות, וקורא את השגיאות שחוזרות.

לכן הוא סוגר את הלולאה לבד: כתיבה ← הרצה ← שגיאה ← תיקון.

לפני שהוא משנה קובץ או מריץ פקודה הוא מבקש אישור. זו נקודת הבקרה שלכם — קראו מה הוא עומד לעשות לפני שאתם מאשרים.

שלושה עקרונות שמנחים את השיעור

נשארים ב-Claude Code. כלי אחד, בלי לקפוץ בין SSMS / טרמינל / דפדפן.

הקבצים הם מקור האמת. Markdown ו-.sql ב-git. בסיס הנתונים הוא רק תוצר נגזר.

בודקים מה ש-Claude מייצר. הוא מהיר אבל לא זהיר. דילוג על בדיקה = שגיאות שקטות לאורך כל הסמסטר.

מכסת הטוקנים — לפני שמתחילים

מנוי Pro ב-20$ מספיק לשיעור — אם לא מבזבזים. שתי החלטות קובעות הכול:

מודל מתי
Sonnet ברירת המחדל לכל השיעור
Haiku שלבים מכניים: SQL, קוד תבניתי, מסכים חוזרים
Opus לא ב-Pro — שורף את המכסה מהר

/model sonnet · /model haiku · /usage מראה כמה נשאר

מה שמבזבז יותר מהמודל: שיחה ארוכה

בכל הודעה, Claude שולח את כל השיחה מחדש. שאלה קצרה בשיחה בת שלוש שעות עולה כמו כל ההיסטוריה.

  • /clear בין שלבים — חינם לגמרי. זה הכלי מספר אחת
  • /compact אינו חינם — הוא עצמו בקשה גדולה
  • נסמן 🔄 בשקפים איפה לנקות

חשבון משותף לקבוצה? המכסה היא של החשבון, לא של המחשב — ארבעה במקביל מרוקנים אותה פי ארבע. עדיף אחד מריץ, השאר בודקים.

שלוש הודעות שקל לבלבל ביניהן

“Context low” — לא מגבלת מנוי. ההקשר התמלא. /clear וממשיכים.

“You’ve hit your session / weekly limit” — מגבלת המנוי, משותפת לכל המודלים. מעבר ל-Haiku לא יעזור; צריך לחכות לאיפוס.

“You’ve hit your Opus limit” — מגבלה של מודל אחד. כאן מעבר ל-Sonnet או Haiku מחזיר אתכם לעבודה מיד.

דרישות קדם

סדר ההתקנה החכם (נבדק על סטודנטים):

  1. התקינו VSCode + Claude Code ידנית (~10 דקות)
  2. תנו ל-Claude להתקין את השאר — Git, uv, .NET, VS, SSMS
  3. הקימו את בסיס הנתונים — Azure SQL (מומלץ, חבר אחד לכל הקבוצה) או SQL Server מקומי

כשהתקנה נתקעת, Claude קורא את השגיאה ומתקן — בלי לחפש stack traces לבד בגוגל.

דרישות קדם — אימות

בטרמינל חדש, שלוש הפקודות חייבות להצליח:

dotnet --version
git --version
uvx --version

בנוסף: Claude Code מחובר, Visual Studio נפתח (2022 או 2025), ו-SSMS מתחבר לבסיס הנתונים של הקבוצה.

בסיס הנתונים: Azure SQL (מומלץ) או SQL Server מקומי.

כל הפרטים וה-Prompt להתקנה ב-PREREQS.

Session ו-Workspace — מה Claude רואה

Workspace = התיקייה שפתחתם ב-VSCode (File → Open Folder). זה כל מה ש-Claude רואה — קובץ שנמצא מחוץ לתיקייה הזו לא קיים מבחינתו. אין צורך ליצור קובץ workspace.

Session = השיחה הנוכחית. כל מה שנאמר בה הוא ההקשר (context) — ולכן שיחה ארוכה עולה יותר.

כשסוגרים, השיחה לא ממשיכה מעצמה. הקבצים נשארים.

/clear פותח Session חדש באותה תיקייה. מה שחשוב נכתב לקובץ — לא נשאר בצ׳אט.

שלב 0 — התיקייה

לפני שפותחים את VSCode. טעות ההקמה הנפוצה ביותר.

  • תיקייה ריקה לחלוטין, למשל C:\projects\sad-groupname
  • תת-תיקייה ריקה בשם docs בתוכה
  • ב-VSCode: File → Open Folder ← בוחרים את התיקייה הזו

לא על שולחן העבודה (OneDrive נועל קבצים), בלי עברית בנתיב, בלי רווחים.

Claude קורא מהתיקייה שפתחתם. תיקייה שגויה = קבצים שגויים.

מה זה MCP

MCP (Model Context Protocol) — תקן אחיד לחיבור כלים חיצוניים ל-Claude. כמו שקע USB: שקע אחד, התקנים שונים. אנחנו מחברים אליו את בסיס הנתונים.

בלי MCP: Claude כותב לכם SQL. אתם מעתיקים ל-SSMS, מריצים, ומעתיקים את השגיאה חזרה אליו.

עם MCP: Claude מריץ את ה-SQL בעצמו, רואה את התוצאה ואת השגיאה, ומתקן.

ההגדרה יושבת ב-.mcp.json בתיקיית הפרויקט — ושם גם פרטי ההתחברות. הקובץ הזה לא עולה ל-git.

שלב 1 — הקמת הפרויקט

  • קובצי ה-PDF לתוך docs/
  • בקשו מ-Claude לבצע git clone … cloned — לא מהטרמינל (git לא תמיד נמצא ב-PATH של הטרמינל)
  • בקשו מ-Claude ליצור .gitignore ← cloned/ + .mcp.json

ואז Prompt אחד מתקין את ה-MCP, מתקן שני באגים בחבילה, ומאמת את החיבור לבסיס הנתונים.

💾 commit: .gitignore וה-commit הראשון של הפרויקט.

עבודה עם git בקבוצה

Repository אחד לקבוצה. חבר אחד יוצר אותו, השאר מתווספים כ-Collaborators ומשכפלים.

השגרה בכל ישיבת עבודה: משכו (pull) ← עבדו ← commit ← דחפו (push).

  • 💾 בשקפים מסמן נקודת commit מומלצת
  • בקשו מ-Claude להריץ את פקודות ה-git — הוא יודע גם לפתור קונפליקטים
  • לא עולים ל-git: .mcp.json, app.config, cloned/, bin/
  • שינוי סכמה נכנס ל-scripts/*.sql ואז push — לא ידנית בבסיס הנתונים

חלוקת עבודה, קונפליקטים וטבלת נקודות ה-commit — הכול ב-GIT_GROUP_WORKFLOW.

שלב 4 — מוסכמות מרכזיות

  • מפתחות ראשיים נקבעים ב-C#, לא ב-DB. בלי IDENTITY.

שלבים 5.6 + 5.7 — המסך הראשון והרצה

5.6 — יצירת מסך ה-CRUD הראשון לישות בסיס. חיברו אותו תחת מסך הבית של התפקיד הנכון.

5.7 — כאן עוברים ל-Visual Studio. הבנייה נשארת אצל Claude, אבל את האפליקציה מריצים משם:

שלב 7 — מכונות מצבים (שיעורי בית)

לא נלמד בשיעור — מופיע כאן כדי שתדעו מה הצעד הבא.

CRUD מתייחס לישויות כאל אוסף שדות. מכונות מצבים מוסיפות:

  • Guards — לא כל מעבר חוקי תמיד
  • תופעות לוואי — ביטול הרשמה ← שחרור מקום + החזר קרדיט
  • אטומיות — BEGIN TRAN … COMMIT

כל מעבר שמופעל על ידי משתמש מקבל כפתור פעולה ייעודי, לא כפתור Update גנרי.

שלב 7 — למה זה חשוב

דיאגרמות המצבים שלכם משיעורי העיצוב הופכות לקוד רץ.

אם תעשו רק CRUD, סטודנטים יוכלו לשנות ידנית status = 'Cancelled' ולעקוף בשקט את כל ה-Guards — תחום שבור.

מכונות מצבים הן המקום שבו הלוגיקה העסקית חיה בקוד, ולא במסכים.
